# Approach write-up (BookLeaf Author Support Portal)

**What I prioritised.** I followed the brief's guidance to put the core ticket loop and the AI integration first: an author raises a query, it gets triaged automatically, an admin opens it with a grounded draft ready, edits and sends it, and the author sees it without refreshing. Every step is covered by an end-to-end test. Next came the API guarantees reviewers will probe: JWT auth on every route, role checks via FastAPI dependencies, authors scoped to their own data (others' tickets return 404), Pydantic validation, and one consistent error format.

**AI design.** The AI assists the team. It never acts on its own. Triage runs in the background after the ticket is saved, so authors never wait and an outage can't block ticket creation. The model is Google Gemini (`gemini-3.6-flash`, with `gemini-3.5-flash` as a backup model). Classification is a tiny JSON-output call with no knowledge base, validated against the allowed labels. Drafting sends only the relevant knowledge-base section plus the one book's real figures, with explicit tone rules taken from BookLeaf's guidelines. Drafts are cached, and token usage is logged. If the model is missing, slow, rate-limited or returns junk, the system falls back to keyword rules and to templates filled with the author's actual numbers, and the UI says so. Admin overrides are tracked (`source = admin`) and never overwritten by a late AI result, which also gives a natural accuracy metric.

**Trade-offs.** A build-free Vue SPA and SQLite locally keep review setup to one command; production runs the same models on Supabase Postgres on Vercel (seeded once under an advisory lock). Polling every 4 seconds instead of WebSockets: it's simpler, works behind any host, and feels real-time for a support desk. In-process background tasks instead of a job queue. Attachments are UI-only, as allowed. A shared demo password for seeded authors, since the dataset has none.

**Evolving to production.** Alembic migrations and Row Level Security, a Redis-backed queue for AI jobs with retries, and SSE/WebSockets via pub/sub for multi-instance real-time. S3 uploads and email notifications on replies. An evaluation set built from real tickets to tune the classifier, with the admin override rate tracked on a dashboard, and approved replies reused as few-shot examples. Retrieval over the full help centre as the knowledge base grows. SLA timers and auto-escalation for Critical tickets. Audit logs and per-agent workload views for the ops team.
